# comment / commentSimple 组件升级说明

> 适用组件：`src/components/comment`（完整版）、`src/components/commentSimple`（简化版）
> 变更日期：2026-10-07
> 结论：**向后兼容的行为增强，无破坏性变更**，升级方基本无需改动业务代码。

---

## 一、变更概览

本轮对两个评论组件做了三类改动：

1. **乐观更新插入位置规则**：发表/回复后，新内容出现在「符合直觉」的位置。
2. **滚动联动**：发表一级评论回到评论区顶部；回复后让新回复滚入视口。
3. **回复输入框单例互斥**（修复多输入框问题）：同一时刻全局只允许一个回复框，切换回复目标时旧框自动关闭。

---

## 二、行为变更详情

### 1. 乐观更新插入位置

| 操作 | 新内容出现位置 |
|---|---|
| 发表一级评论 | 评论列表**第一个位置（顶部）**，并自动切换到「最新」排序 |
| 回复楼主 | 该楼 `replies` 的**第一个位置（楼顶）** |
| 回复楼中楼 | **被回复那条回复的正下方**（楼中楼之间），而非列表末尾 |

> 数据仍为扁平结构：回复统一挂在一级评论的 `replies` 数组中，不引入嵌套层级。

### 2. 滚动联动

- **发表一级评论**：瞬间回到评论区顶部（虚拟滚动模式滚列表视口，非虚拟模式 `scrollIntoView` 对齐，无动画）。
- **回复（楼主 / 楼中楼）**：发送后自动展开该楼回复列表，并把刚发的新回复**最小幅度滚动进入视口**（`scrollIntoView({ block: 'nearest' })`：已可见则不动，仅在视口外时才滚动）。不会跳到整个评论区顶部，避免把用户带离当前楼层。

### 3. 回复输入框单例互斥（核心修复）

**修复前的问题**：回复框的显隐状态由每个 `CommentItem` 实例各自维护，导致回复不同楼主/楼中楼时会**同时出现多个回复输入框**。

**修复后**：「当前激活的回复框」提升为**父组件持有的单例状态**（内部 `activeEditor = { commentId, replyId }`）。效果：

- 同一时刻**全局只有一个**回复输入框；
- 在 A 楼打开回复框后，再去 B 楼打开 → A 的框自动关闭；
- 编辑器位置仍就近：`replyId = null` 置顶（回复楼主），否则插在对应楼中楼正下方。

## 三、接口变更（向后兼容）

### `reply` 事件 payload 新增字段

组件向父组件抛出的 `reply` 事件负载**新增** `replyToId` 字段：

```js
// 旧：{ commentId, content, replyTo, opId }
// 新：{ commentId, content, replyTo, replyToId, opId }
{
  commentId: "c1",          // 所属一级评论 id
  content: "回复内容",
  replyTo: { id, name } | null,  // 被回复作者（用于展示「A 回复 B」）
  replyToId: "r1" | null,   // 【新增】被回复的回复 id；null = 回复楼主
  opId: "op_xxx",           // 乐观更新操作 id（用于 settle / rollback）
}
```

- `replyToId` 为**纯新增字段**，原有字段不变，已有监听代码不受影响。
- 该字段可用于业务侧区分「回复楼主 / 回复楼中楼」及定位插入锚点（组件内部已按此规则处理，业务侧一般无需额外处理）。

### Props / 其它事件

- **无新增必填 prop，无删除/重命名 prop，无破坏性变更。**
- `send` / `like` / `delete` / `load-more` 等事件及其负载均不变。

## 四、升级步骤

1. 用新版本组件替换旧版本（两个组件目录整体更新）。
2. **业务代码无需改动**即可获得上述全部行为增强与多输入框修复。
3. （可选）若业务侧希望区分回复目标，可在 `@reply` 回调中读取新增的 `replyToId`。

```js
// 可选：利用新增字段
const onReply = ({ commentId, content, replyTo, replyToId, opId }) => {
  if (replyToId == null) {
    // 回复楼主
  } else {
    // 回复楼中楼，被回复的回复 id = replyToId
  }
};
```

## 五、迁移注意点

- **`replyTo` 数据格式**：组件内部新建回复时写入的 `replyTo` 为 `{ id, name }` 嵌套对象。若你的后端返回的是「平铺」格式（如 `replyToId` / `replyToName` 顶层字段），需注意：
  - 回复框显隐、插入位置**不受影响**（它们不依赖 `reply.replyTo`）；
  - 仅「A 回复 B」的展示文案（[ReplyItem](file:///d:/vue3-vxe-table/src/components/comment/components/ReplyItem.vue) 读取 `reply.replyTo.name`）会受影响，需保持 `replyTo` 为 `{ id, name }` 结构，或同步调整展示读取字段。
- **数据量大时的性能**：主列表（一级评论）已支持虚拟滚动；楼中楼（ReplyList）当前为全量渲染。若存在「单楼上千条回复」的热帖，回复触发的自动展开会一次性渲染该楼全部回复，建议结合数据量级评估是否需要对楼中楼做窗口化。
